Clause 7.5 of https://www.iso.org/standard/27001[ISO/IEC 27001:2022] asks for the control of documented
information: versioning, review and approval, availability, protection against change, traceable changes. Read with
a developer's eyes, that is a description of a Git server with protected branches. The ISMS category takes the hint,
carefully: it is an extension of Audit Notary for development organisations, not a replacement for a complete ISMS
product.

== The ISMS on Git

[cols="1,1"]
|===
|Clause 7.5 |Git

|Versioning, change history |commits, diff
|Review and approval |release in the application with step-up, signed release commit, protected `main`
|Protection against unauthorised change |repository rights, protected branches and tags
|Availability and retention |the Git server and its backup
|===

The ISMS artefacts sort into three groups:

. *Documents, very well suited*: policies, scope, internal audit and management review reports. Rarely changed,
  approval-centred, diffable.
. *Registers, well suited*, with the pattern of xref:category-samm.adoc[SAMM] (one file per entry, in-memory index,
  compare-and-swap). The first iteration keeps the risk register only. The in-memory index rests on the design
  assumption that a mid-sized ISMS holds at most a few thousand register entries; a measurement of index build time and
  memory at that size has to confirm it before the register is built.
. *Operational data, referenced instead of stored*: tasks and deadlines (issue tracker of the Git server or Jira), the
  live handling of incidents (ticket system; the report on an incident is a schema-driven document, see
  xref:category-incident-reports.adoc[Incident Response Reports]), training records per employee (learning platform or
  HR system). Persons, roles and teams come from the library's
  https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/directory-and-catalogs.adoc[directory], the services from the
  xref:service-catalog.adoc[service catalog].

=== Mechanisms the ISMS Uses

All of these are library mechanisms; the ISMS category uses them and adds no mechanism of its own.

* *Releases in the repository*: the application merges every release itself; the signed release commit names the
  releasing user, so the evidence survives a change of Git server
  (https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/identity-and-signing.adoc[Identity and Signing]).
* *Running numbers* (R-042) under concurrent creation: a ULID identifies a new entry until its first save, which
  assigns the readable number that then names the entry file
  (https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/schema-driven-documents.adoc[Schema-Driven Documents]).
* *Reporting dates*: "the risk register as of the audit on 1 March" is a tag or the commit of that date; the index
  is built from it.
* *Deadlines and reminders* are computed from the index; notifications are runtime state of the application, not
  persistence.

=== The Bridge to SAMM

A gap between a SAMM score and its target may become a risk in the register, with a reference to the released
assessment. Once controls are kept, a released assessment becomes evidence for the secure-development controls of
ISO/IEC 27001:2022, among them A.8.25, by a reference to its tag. Both domains run on one engine.

=== Limits

* Real-time incident handling with escalation is no case for Git; it stays in the ticket system.
* Queries across many repositories need an instance that may read all of them, or queries run with the user's rights
  and show only what the user may see.
* The process description of the control of documented information has to be written once per organisation (see
  xref:audit-notary-overview.adoc#_positioning[Overview, Positioning]).

== Comparison with verinice

verinice is an ISMS product of SerNet. The classic product is a Java application whose user interface is built on the
Eclipse Rich Client Platform (https://github.com/SerNet/verinice[verinice on GitHub]), with the server verinice.PRO,
which needs a PostgreSQL or Oracle database; SerNet names domains for BSI IT-Grundschutz, ISO/IEC 27001, TISAX,
NIS 2, data protection and BCM (https://verinice.com/en/products/verinice/verinicepro-server[verinice.PRO]). verinice.veo is the
web-based new generation, offered as verinice.cloud by SerNet or as verinice.onprem for operation in a data centre
(https://verinice.com/en/veo[verinice.veo]); it consists of several microservices that need Keycloak, PostgreSQL and
RabbitMQ (https://github.com/SerNet/verinice-veo[verinice-veo on GitHub]).

[cols="1,2,2"]
|===
|Criterion |Audit Notary (Git) |verinice / verinice.veo

|Domain content
|Built by the project. The IT-Grundschutz-Kompendium is published by the BSI as a download
(https://www.bsi.bund.de/DE/Themen/Unternehmen-und-Organisationen/Standards-und-Zertifizierung/IT-Grundschutz/IT-Grundschutz-Kompendium/it-grundschutz-kompendium_node.html[IT-Grundschutz-Kompendium]);
the text of ISO/IEC 27001:2022 is not part of the project, only own wording and the clause and control numbers
|Domains for Grundschutz, ISO/IEC 27001 and others in the product; for veo, SerNet announces the content of catalogs,
compendia and standards and preinstalls it on the server (verinice.veo page)

|Reports (statement of applicability, Grundschutz check, risk report)
|Built by the project
|In the product; verinice.PRO customises reports with vDesigner (verinice.PRO page)

|Operation
|Application and existing Git server; backup, rights and reviews exist
|veo: microservices with Keycloak, PostgreSQL and RabbitMQ on premise, or verinice.cloud operated by SerNet

|Versioning, diff, reporting dates
|Every change is a commit, any two states compare as a diff, a reporting date is a tag or a commit
|veo keeps every change of an object as a version: the History sidebar shows and restores earlier versions
(https://github.com/SerNet/verinice-veo-web-documentation/blob/main/docs/en/manual/objects.md[veo manual, Objects]),
and the veo-history service returns all revisions of a resource and the one current at a point in time
(https://github.com/SerNet/verinice-veo-history[verinice-veo-history]); the History section of the manual names no
comparison between versions

|Approval and tamper evidence
|Release with step-up in signed commits, protected branches, anchored releases and periodic checkpoints, verifiable
without the application
|verinice.PRO names a web-based workflow with mail notification (verinice.PRO page); the sources checked name no tamper
evidence

|Rights
|Coarse per repository, cut by confidentiality; enforced by the application
|verinice.PRO names a granular authorization and role concept (verinice.PRO page); veo manages users and access rights
in Keycloak (https://verinice.com/en/ressources/learn/technical-background[verinice technical details])

|Data sovereignty
|Plain YAML or AsciiDoc files, readable with any text editor
|Database; veo offers a public, documented programming interface
(https://verinice.com/en/ressources/learn/interfaces-apis[Interfaces and APIs])

|Acceptance by auditors
|Has to be explained (process description of the control of documented information)
|Not checked against a source; SerNet names BSI and ISO licences for verinice (verinice.PRO page)
|===

=== Positioning

From this comparison follows the positioning: Audit Notary complements verinice and does not compete with it as a
complete ISMS. Core and extension are listed in xref:audit-notary-overview.adoc#_positioning[Overview, Positioning].

== Open Questions

. Verify the verinice statements (approval, licence of veo, catalogue coverage) with a demo instance.
. Deferred: the registers of controls, suppliers, nonconformities and non-application assets, the statement of
  applicability, and audit tags that mark a reporting date.

Decided provisionally with the Reports lens (UC-ISMS-3), recorded in
xref:../specification/rest-api.adoc#_decided_reports[REST API Register, Open Questions]; the owner may change each one:

. The risk register as of a date is a report of the lens *Reports* (`/reports/risk-register?as-of=`): a calendar date (UTC)
  or a tag name, released entries only, each as a summary (number, title, rating, treatment, owning team, version, release
  time, review date, origin) that opens the entry as it was then. The fields of a risk are fixed with the ISMS lens.
. The application creates no reporting tag; the picker lists the tags that exist.

Decided provisionally with the ISMS lens (UC-ISMS-1, UC-ISMS-2, UC-SAMM-6, UC-TM-3), recorded with the bodies in
xref:../specification/rest-api.adoc#_decided_isms[REST API Register, Open Questions]; the owner may change each one:

. The four document types and the risk are documents of the generic lifecycle, each released more than once and under one
  workflow (`isms.submit`, `isms.release` with step-up); a document is a single file with its AsciiDoc fragments as fields, and
  the generated output is not part of the web app. The fields are provisional: an owner role, the main text and a review date
  for a document, an owning team, a rating, a treatment and measures as issue ids for a risk. Two versions are compared with the
  diff of the document lifecycle, at `/isms/documents/<id>/compare`.
. The first save of a risk assigns its running number and nothing is stored before it: the page `/isms/risks/new` shows no
  number, never predicts one, and moves to the entry when the number is known; numbers are never reused and need not be
  consecutive. The register as it is worked on (every state) is `GET /api/v1/isms/register`; the register as of a date is
  unchanged.
. A gap of a scope and a threat become a risk through a prefilled form, never without the person saving it: the risk keeps the
  reference to the practice or the threat as a read-only `origin`, one risk at a time per origin, and the rating is the person's.
  The transfer of a threat is recorded in the threat model by the application when the risk is saved for the first time, which
  makes a released model a draft; the alternative is to derive it from the register.
. The register has no deletion, retirement or closing of a risk, and no acceptance by a manager before the release; whether
  the standard asks for the acceptance of a residual risk by the risk owner is not checked here. A review date is typed, not
  computed, and the Due lens lists the reviews of released entries only.

Decided provisionally with the documents of the ISMS lens (UC-ISMS-1), recorded in
xref:../specification/rest-api.adoc#_decided_isms[REST API Register, Open Questions] (points 77 to 84); the owner may change each one:

. The first column of the lens lists the four document types with their counts and the way into the risk register; the documents of a
  type are the second column, the document its sheet. The sheet, the release and the earlier states are those of the generic lens on the
  addresses of the lens ISMS, which is no generic category.
. Two releases are compared on a page of its own, `/isms/documents/<id>/compare`, whose pickers offer the releases and, for the later
  side, the current state; the page reads the generic diff of two revisions and shows the changes as the release page does. The commits
  between two releases are read with `?at=` on the sheet.
. The review date of a document is a fact under its title, in words and without a colour of its own; the list shows none, because the
  summary of a document has no review date. Whether it should is an owner question.
. A policy that applies to everyone names the reference `team:organisation`; no specification says that the team catalog holds it.
. Opening a document from *All documents* shows the list of its type, because the address of a sheet carries no `kind`.
. A comparison the server refuses is worded by the page, not by the form.
