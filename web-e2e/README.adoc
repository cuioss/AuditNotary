= Audit Notary Web E2E
:toc: left
:toclevels: 2

The end-to-end suite of the web app: Playwright and axe-core against the Vite dev server of `web-app`, whose `/api`
and `/mock` go to `web-mock` (`doc/specification/testing.adoc`, AUN-TEST-1; the reasoning is ADR-0003). The global
setup starts the mock through `web-mock/start.sh` (profile `workshop`, timing `ordered`) unless one already answers,
and the tests switch profiles through its control routes.

== Running

[source,bash]
----
./mvnw verify -Pe2e -pl web-e2e -am     # through Maven: npm ci, lint, playwright install chromium, playwright test
cd web-e2e && npx playwright test       # directly, after npm ci
npx playwright test tests/login.spec.js # one spec
npx playwright show-report target/playwright-report   # the HTML report of the last direct run
----

Without the profile `e2e` the module only installs and lints; Maven runs the suite with the `list` reporter only.
The suite runs with one worker: every spec changes the state of the one mock server.

Ports: `AUDIT_NOTARY_WEB_PORT` (5173) and `AUDIT_NOTARY_MOCK_PORT` (7420), named only in `tests/helpers/ports.js`
(`scripts/guard-ports.js`).

A new view gets its address in `navigation.spec.js` and its audit in `theme-readability.spec.js`; a new profile of
`web-mock` gets the spec of the flow it exists for.

The clock of the page is the real one. A spec that tells a deadline or a review date (`incidents.spec.js`, `incidents-release.spec.js`, `isms.spec.js`, the audit rows and the
phone checks of the lenses Incidents and ISMS) pins it with `pinClock` to `2026-11-26T10:00:00Z`, the instant the mock reads at, and a test that wants
another day (a deadline the page has overtaken) pins that and reloads.

A test that depends on the state of the mock says so: `useScenario` checks that the mock answered the profile and the
state it was asked for, and the audit rows of `theme-readability.spec.js` that read what a state answers check it again
(`expectScenario`) once the page is up. The mock is one shared instance and `web-mock/stop.sh` stops the one in its PID
file, so two runs that use one mock (or one that stops it under another) can show up as a named mismatch or as a refused
connection, but the checks are checkpoints and not isolation: a check that names only the profile passes while another run has
switched the mock to another state of that profile, and a page may read a state between two checks. Give every concurrent
run its own ports.

The mock stores nothing, and a state it has no profile for is not invented in the page. Where a flow needs one, the test
says so in a comment, by one of two ways:

* For something the server does not hold, or a read the person may not make (an incident the server does not know, a year the
  person may not read, an answer that fails), the test answers the read with `refuseRead`, which gives the status and the body
  directly and fetches nothing. A write the mock has no state for (a create refused for the year of the awareness, a create that
  asks for a fresh login) is answered the same way with `page.route`, for that request only, and the request never reaches the
  mock.
* For a state the server holds but the page must read differently, the test fetches the real answer and changes it with
  `patchRead` (a stage the page reads as open that the server knows does not apply, a released incident with a deadline that
  was open at the release, an incident in review with deadlines still open, a local user who is asked for the password, a trend that leaves versions out, a scope whose targets
  another assessor saved, a scope that shows no open assessment while the server knows one, fifty evidence links, a sixth scope
  in the trend, a third released assessment, a session that reads no register, a register that answers `FORBIDDEN`). With
  `times` only the first reads are changed, so that a read the page makes after a refusal brings the mock's own answer.

== Cold start

Vite transforms a module when it is first requested, and the first page of a run asks for about 700 of them. The first
test of a run (`access.spec.js`, a deep link without a session that must reach `/login` within the default timeout of
5 s) used to pay for that: measured on a quiet machine with a fresh dev server, the redirect took 2.0 to 3.5 s on
`main` and on the branch alike (0.35 to 0.45 s once the pages were loaded before), and the whole test 5.6 to 6.3 s
against 1.1 s. On a busy machine the cold redirect passes 5 s and the test fails; it is the same on `main`.
`global-setup.js` therefore loads `/login` and the shell once, in a browser, before the first test and waits for the
pages themselves (`login-view` or `view-title`, up to 120 s), never for a duration. A failed warm-up is a warning; the
tests then say what is wrong.
