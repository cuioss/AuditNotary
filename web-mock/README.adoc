= Audit Notary Web Mock
:toc: left
:toclevels: 2
:source-highlighter: highlight.js

A mock server of the `/api/v1` requests of the Audit Notary web app, driven by scenario files. The web unit tests, the
end-to-end suite (`web-e2e`) and manual work on views run against it instead of the application, the identity provider
and a Git server. Specification: `doc/specification/testing.adoc`, AUN-TEST-1; decision:
`doc/adr/0003-UI_tests_run_against_a_scenario_mock_server.adoc`. Development and tests only; never deployed.

Plain Java 25: the JDK HTTP server on `127.0.0.1`, one virtual thread per request, Jackson. The message catalogue
and the canonical addresses come from the `audit-notary-web-app` JAR (`META-INF/audit-notary/`).

== Start and Stop

[source,bash]
----
web-mock/start.sh -s workshop            # background; PID and log in web-mock/target/
web-mock/start.sh -s first-login -p 7421 -t ordered
web-mock/start.sh -f                     # foreground
web-mock/stop.sh
----

`start.sh` compiles when a source is newer than the last build; the build of `web-app` then contributes its resources
only (no Node build). On start the mock logs one line, which `start.sh` waits for:

----
WEB_MOCK-1: Web mock listening on http://127.0.0.1:7420 with scenario workshop#ready, timing REALISTIC
----

[cols="1,1,3"]
|===
|Option |Default |Meaning

|`-s`, `--scenario`
|`workshop`
|A profile name, `name#state`, or the path of a scenario file (optionally with `#state`)

|`-p`, `--port`
|`$AUDIT_NOTARY_MOCK_PORT` or `7420`
|Port on `127.0.0.1`; `0` takes any free port

|`-t`, `--timing`
|`realistic`
|`realistic` waits for the delays of events and timed transitions; `ordered` plays them at once, in file order

|`-h`, `--help`
|
|Prints the usage
|===

Without the scripts: `java -cp … de.cuioss.notary.audit.mock.cli.WebMockCli --scenario workshop`, or
`./mvnw -pl web-mock exec:java -Dexec.args="--scenario workshop"`. From a JUnit test:
`try (var mock = WebMock.start("workshop", 0, Timing.ORDERED)) { … }`.

== What the Mock Emulates

* *Login provider:* the scenario's `login` names `oidc` (default) or `local`. With `oidc`,
  `GET /api/v1/auth/login?return=<address>` signs in as the scenario's user without an identity provider: it sets the
  cookie `audit-notary-mock-session` (`HttpOnly`, `SameSite=Strict`, `Path=/`; not `Secure`, the mock runs
  on plain HTTP) and answers a page that navigates to the checked `return` by `<meta http-equiv="refresh">`, no
  script. A `return` that is not a canonical address becomes `/` (the pages outside the shell, such as `/login`, are no
  valid `return`). Every other `/api/v1` request without session answers `401 UNAUTHENTICATED` with `login`:
  `/api/v1/auth/login` with `oidc`, `/login` with `local`. With `local` the login start creates no session: it answers
  `302` to `/login?return=<checked address>`, and `POST /j_security_check` (form body `j_username`, `j_password`; `404`
  with `oidc`) answers `200` with an empty body and the cookie for a user of `login.users`, `401` with an empty body for
  anyone else, and `403 CSRF_REJECTED` when `Origin` is missing or foreign. No anti-CSRF header is needed there. The
  password is never recorded in `/mock/acts`: the field `j_password` is redacted like `password`.
* *Refused logins:* a route of a scenario or state for `GET /api/v1/auth/login` or `GET /api/v1/auth/callback` is the
  answer of that request (it replaces the built-in login; with a callback route the built-in login does not sign in
  but navigates to the callback). For a browser navigation (`Accept` contains `text/html`) the outcomes
  `IDENTITY_PROVIDER_UNAVAILABLE`, `TOO_MANY_LOGINS` and `UNKNOWN_TRANSACTION` are answered as `303` to
  `/login-problem?reason=idp-unavailable|too-many-logins|unknown-transaction` without body; every other client gets the
  JSON. A `503` with the outcome `TOO_MANY_LOGINS` carries `Retry-After: 60`, whichever request it answers.
* *No rights:* with `"rights": []` and no first login, every `/api/v1` request outside the shell answers
  `403 FORBIDDEN` before the routes are looked at; the shell includes `POST /api/v1/directory/me/confirmation`.
* *Requires:* a route or link with `requires` the user's rights do not hold answers `403 FORBIDDEN` (_Path Templates and
  requires_).
* *Session changes:* a state with `"session_replaced": true` closes every open event stream on entry and replaces the
  anti-CSRF token of every session (the cookie stays valid; a request with the old token answers `403 CSRF_REJECTED`);
  a state with `"session_ended": true` closes the streams and drops every session.
* *Anti-CSRF and Origin:* every state-changing request must carry `X-CSRF-Token` with the token of
  `GET /api/v1/session`; an `Origin` header must be the own origin, which is `X-Forwarded-Proto://X-Forwarded-Host`
  behind the Vite proxy (`xfwd: true`), otherwise `http://<Host>`. Otherwise `403 CSRF_REJECTED`.
* *First login:* while `first_login_required` holds, every request outside the allow-list of AUN-DIR-2 answers
  `403 FIRST_LOGIN_REQUIRED`.
* *Built in:* `GET /api/v1/session`, `POST /api/v1/auth/logout` (answers `{"redirect": "/signed-out"}`, the
  page of the web app, and clears the cookie), `GET /api/v1/messages?lang=en|de` (`400` for another language) and
  `GET /api/v1/events`.
* *Unknown documents:* a request about one document (`/api/v1/documents/<repository>/<id>[/...]`, `/api/v1/drafts/...`,
  `/api/v1/releases/...`) that no route or link answers and whose repository the scenario's rights name answers
  `404 {"outcome": "NOT_FOUND"}`, as the real server does for a document that does not exist; any other unrouted request
  answers `404 MOCK_NO_ROUTE`.
* *Event stream:* `text/event-stream`, frames `id:`, `event:`, `data:`; a `: keepalive` comment every 15 s. Events
  come from entered states and `POST /mock/broadcast`; switching, resetting or jumping first announces the new
  `status`.

== Control Routes

No login; the Vite dev server forwards `/mock` for loopback clients only.

[cols="1,3"]
|===
|Request |Effect

|`GET /mock/state`
|`{"scenario", "state", "description", "first_login_required", "directory_confirmation_due", "timing", "links": [{name, method, path, next}]}`

|`GET /mock/scenarios`
|`{"primary": [...]}`

|`POST /mock/scenario`
|Body `{"scenario": "name[#state]"}` (or `?name=`): switches the profile; keeps the sessions, clears the acts

|`POST /mock/goto/{state}`
|Moves to a state of the active profile and plays its events

|`POST /mock/reset`
|Back to the start state; clears the acts; keeps the sessions

|`POST /mock/broadcast`
|Body `{"event", "data"}`: pushes one event to every open stream

|`GET /mock/acts`, `DELETE /mock/acts`
|The recorded state-changing `/api/v1` requests `{method, path, state, body}`, the path with its query as sent; clears them

|`POST /mock/sessions/clear`
|Drops every session
|===

== Scenario Format

[source,json]
----
{
  "format_version": 1,
  "name": "workshop",
  "description": "…",
  "login": { "provider": "local", "users": [ { "username": "alex", "password": "local-password" } ] },
  "user": { "pseudonym": "p-4c1a9e", "name": "Alex Example", "groups": ["samm-assessors"] },
  "rights": [ { "repository": "samm-assessments", "actions": ["read", "edit"] } ],
  "first_login_required": false,
  "directory_confirmation_due": false,
  "start": "ready",
  "routes": { "GET /api/v1/status": { "status": 200, "body": { } } },
  "states": {
    "ready": {
      "description": "…",
      "first_login_required": false,
      "directory_confirmation_due": false,
      "session_replaced": false,
      "session_ended": false,
      "routes": { "GET /api/v1/due": { "status": 200, "body": { } } },
      "links": { "save-entry": { "method": "PUT", "path": "/api/v1/directory/me", "next": "registered",
                                  "status": 200, "body": { } } },
      "events": [ { "after_ms": 0, "event": "document-saved", "data": { } } ],
      "auto": { "after_ms": 1500, "next": "other" }
    }
  }
}
----

* A request is answered by the first of: a link of the current state with the same method and path (moves to `next`
  and plays that state's events and timed transition), a route of the state, a route of the scenario; otherwise
  `404 MOCK_NO_ROUTE`.
* `login` is optional; the default is `{"provider": "oidc"}`. `users` belongs to `local` only, each user has a
  non-empty `username` and `password`. `session_replaced` and `session_ended` are optional booleans of a state (default
  `false`).
* Route keys are `"METHOD /path"` or, with a query, `"METHOD /path?name=value[&name=value]"` (_Query-Keyed Routes_);
  `status` defaults to `200`, `body` to `{}`, `after_ms` to `0`.
* A route or a link answers either its `body` or the JSON of the data file its `body_file` names, below
  `src/main/resources/scenarios/data/` (`"body_file": "samm-scopes.json"`). Large or shared answers live there once
  instead of inline in every profile. The file name matches `[a-z0-9][a-z0-9.-]*.json`; a name that resolves to no
  file, a file that is no JSON, or `body` and `body_file` together fail the load.
* A route (not a link) may instead name a built-in engine answer, `"handler": "render-asciidoc"`,
  `"handler": "search-documents"` or `"handler": "catalog-entry"`; it then carries no `body`, `body_file` or `status`, and an unknown handler name fails
  the load (see _Fixture Categories_, _Document Lifecycle_ and _Directory and Catalogs_). The handlers
  `search-documents` and `catalog-entry` need a `data_file`, the data file of their index or catalog, read like a
  `body_file`; no other handler has one.
* `directory_confirmation_due` (a boolean, default `false`) is a member of the scenario and, as an override like
  `first_login_required`, of a state: the answer of `GET /api/v1/session` carries it as `directoryConfirmationDue`.
* A path may hold `{name}` segments (_Path Templates and requires_); a route or link may carry `requires`.

== Fixtures and Drift Tests

The scenario files and their data files are static fixtures, and the format has no way to derive one list from another
(no generator, no `derive_from`). Where a fixture mirrors another source (the catalog lists and the entries behind them,
the service states and their baseline, the retired snapshot and the dependency graph, the outage refusals and the write
routes, the reserved ids and the routes, the handler ids and `Handler`), a test reads both and fails on drift
(`DirectoryAndCatalogsTest`, `SammCompletionTest`, `ReportsLensTest`, `ThreatModelsTest`, `scenarioFetch.test.ts`). That is the accepted guard (decided provisionally; the
alternative is a scenario-format change that derives the lists when a scenario is loaded).

*The handler `render-asciidoc`* is named by a route (`"handler": "render-asciidoc"`; a route has either a handler or a
`body`/`body_file`/`status`, and the loader accepts only known names). It is a mock, not Asciidoctor, and answers in
this order:

. `422 VALIDATION` with the pointer `/source` and the code `REQUIRED` when the body is no JSON object with a `source`,
or `TYPE` when `source` is no string;
. `413 {"outcome": "TOO_LARGE", "limit": 65536}` when `source` is longer than 65,536 bytes of UTF-8;
. otherwise `200 {"html": …}`: the whole source is HTML-escaped first; blocks are separated by blank lines; a block of
star lines (`* `) is a `<ul>` with one `<li>` per line, a block of one line starting with `== ` to `====== ` is
`<h2>` to `<h6>`, every other block is `<div><p>` with its lines joined by `<br>`; inside a block `*x*`, `_x_` and
`` `x` `` become `<strong>`, `<em>` and `<code>` (non-greedy, not nested). An empty source gives an empty `html`.

The anti-CSRF header is required as for every POST. A render is listed in `GET /mock/acts` like any state-changing
request, with its source (the mock logs no body); it is no save, so tests that assert the acts of an edit filter by
path. The states `preview-hostile` (`render-asciidoc-hostile.json`: script, handlers, `javascript:` and `data:` links,
`style`, `iframe`, `form`, `svg`, an `img`, a table) and `preview-unavailable` (`503 {"outcome": "RENDER_UNAVAILABLE"}`)
replace the handler. A source over the limit needs no state: it answers `413` by itself. The HTTP adapter reads a request body at most up to 12 MiB (`MockEngine.MAX_BODY_BYTES`: six times the
2 MiB of a Backstage import, the worst case of JSON escaping, and far above any source within the limit); a larger body is
answered with `413` before it is buffered, whatever the request. The `limit` is the one of the request: 2097152 for the
import and its preview, 65536 for every other path. A valid import of up to 2 MiB therefore reaches its route.

== Path Templates and requires

*Path templates.* A route or link key may hold a segment `{name}` (name `[a-z][a-z0-9]*`) that stands for exactly one
non-empty segment of the request path: `"PUT /api/v1/catalogs/service/{id}"`. The loader refuses an empty name, a name
twice in one path, and `{` or `}` inside a segment, naming file, location and rule. The order of choice extends the
rule of the _Scenario Format_: a link of the state, a route of the state, a route of the scenario; within one level an
exact path comes before a templated one, then the key with more literal segments, then the one with more listed query
parameters, then (routes) the text of the key. A template never beats an exact key of the same level, and a template of
a state beats an exact key of the scenario. The segments a template stood for are passed to a handler; `/mock/acts`
records the request as sent.

*The handler `catalog-entry`* answers the entry requests of one catalog from its `data_file`
(`{"catalog": "service", "entries": [{"id", "name", "retired", "value", "effective", "at", "history"}]}`; the loader
checks that the file has `catalog` and `entries` and that the route key holds `{id}`). The method decides:

[cols="2,3"]
|===
|Request |Answer

|`GET /api/v1/catalogs/<catalog>/{id}`
|`200` the entry as the register shows it (`catalog`, `id`, `name`, `retired`, `value`, `effective`, `at`, `history`);
an unknown id `404 NOT_FOUND`

|`PUT /api/v1/catalogs/<catalog>/{id}`
|`200 {"outcome": "SAVED", "catalog", "id", "at": "2026-11-26T09:30:00Z"}`; an unknown id `404 NOT_FOUND`, a retired entry
`409 RETIRED`

|`POST /api/v1/catalogs/<catalog>/{id}/retirement`
|`200 {"outcome": "RETIRED", "catalog", "id", "at": "2026-11-26T09:35:00Z"}`, also for a retired entry; an unknown id
`404 NOT_FOUND`
|===

The mock stores nothing: a state decides what the next read shows (`service-retired`, `catalog-changed-elsewhere`).

*`requires`.* A route or link may carry `"requires": {"repository": "directory", "action": "administer-catalogs"}`.
When the `rights` of the scenario do not hold the action on that repository the engine answers `403 {"outcome":
"FORBIDDEN"}` before the route or link is used: a link does not move on. Every catalog and directory write of the
profiles carries it, so `workshop`, `read-only` and the others refuse it without a route of their own.

*Limits.*

* *The answers are static.* A save changes no state except the first one of the checkout flow (the link of `ready`); a `PUT`
of a recipe draft changes none (the draft the wizard reads back is the state `recipe-draft-saved`); the create of the
*Report scheduler* is the only create that moves; creating a model of `notification-gateway` answers `201` and the model is
not readable.
* *A state replaces the keyless route of the model*, so every state of the lifecycle repeats the keyed revisions
(`?at=v1` to `?at=v3`, `v4` in `threat-model-released`, `v9`, `zzz`); a state does not carry the mock's other overrides
(for example the evaluation of `no-threat-models` and a lifecycle state do not combine).
* *The recipe drafts of other services* are `404 MOCK_NO_ROUTE`; `no-threat-models` overrides only the page of the
*Payment API*; the Due list is not derived: the item of the checkout flow stays after the release.
* *`degraded` and `local` do not walk the lifecycle* (no `approve`, no state); `degraded` names `samm-assessments` and, in
`unreachable`, `threat-models` `DOWN` in its status, and refuses the threat model writes there. `local` grants `read` only
on `threat-models`, so its web app offers no edit.
* *A save or a submit after the release is not mocked.* `threat-model-released` reads released as v4; a save or a submit that
reaches the base route there still answers as in `ready` (the opening of v5 is not mocked, and the contract does not yet
define the submit of a released model).
* *The diagram is a fixed drawing*, the evaluation must keep reproducing the figures of _Reports_ (`ThreatModelsTest`
asserts it), and the revision reads exist for the checkout flow (`v1` to `v4`) and the login flow (`v1`) only.

== Query-Keyed Routes

A route key or a link path may carry a query, for example
`GET /api/v1/documents/test-notes/01JZ8W1E3G5J7M9P1R3T5X7Z9B?at=v1`. It matches a request of the same method and path
whose query holds every listed name with exactly the listed (percent-decoded) value; further parameters do not hinder
the match, and a key without query matches any query, as before. The choice among several matches: a link of the state,
a route of the state, a route of the scenario; within one of them the key with the most listed parameters, then the
key without query. Equal routes are told apart by the text of their key, so that the answer never depends on the order of
a map; equal links are not: of several links with the same number of listed parameters the first in the order of the
state wins (`ScenarioState.linkFor`; `web-app/src/lib/test/scenarioFetch.ts` does the same). `/mock/acts`
records the path of a request with its query as sent, and `/mock/state` lists a link with its query.

A key cannot say "this parameter is absent" or "any value but the listed ones", so a request whose query value no key lists
reaches the key without query. This is visible where a fixed set of values has an explicit answer for the rest: an `at` that
is no release of a risk or a document (a commit of a save or a submit, `v8`) answers the current state, not `404` or `422`, and
`GET /api/v1/isms/risks/draft?origin=` with an origin that has no key answers `422 REQUIRED` as the request without `origin`
does. The explicit keys (`v9` and `zzz` of R-004, the unknown threat `T-99`) show the answers of the real server; the mock
does not claim the others. A change of the engine, not of a fixture, would be needed (an owner question).
